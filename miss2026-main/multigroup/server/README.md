# Serveur d'inscription — test uniquement

Phase 1 : recherche, création et adhésion privées. Aucune modification du front, de la régie, des votes ou de Firebase de production. Le registre transitoire est events/miss2027/registration dans le projet strictement contrôlé miss2027-test-v2. Les clients ne doivent jamais avoir de lecture ou d'écriture sur ce registre. Le serveur Admin SDK est le seul écrivain. Les transactions atomiques sur ce registre empêchent la double appartenance entre groupes privés; l'attribution publique devra employer le même index avant son activation.

Le serveur refuse de démarrer sans ENABLE_TEST_REGISTRATION=true et un compte de service du projet test. Ne jamais placer sa clé dans GitHub, VITE_*, ou dans le chat. Configurer le secret directement dans le service serveur Render, distinct du site statique. Ne pas modifier les règles existantes de la régie test. Prévoir une clé à privilèges limités, révocable.

La création exige un ID token Firebase et une adresse e-mail vérifiée. Le secret du groupe est haché via scrypt et sel aléatoire; jamais exposé via la recherche. L'adresse e-mail n'est pas stockée dans le registre. Le mot de passe partagé ne doit PAS devenir le mot de passe Firebase du créateur. Pour la future gestion, authentifier le propriétaire avec un lien de connexion envoyé à son e-mail (ou une autre preuve indépendante de possession de l'e-mail), puis contrôler son UID côté serveur. Une simple propriété email_verified sur un compte à mot de passe partagé ne suffit pas. Gestion et invitations non implémentées à ce stade.

API : GET /health; GET /groups/search?q=...; POST /groups/create {name,pseudo,password}; POST /groups/join {id,pseudo,password}. Les trois dernières exigent Authorization: Bearer <ID token Firebase>. Origine web limitée au site test; CORS n'est pas une authentification. Les limites de tentatives sont provisoires, en mémoire et non distribuées. Il faut tester les abus, la concurrence, les règles, la capacité et l'intégration avant ouverture. La transaction sur le registre entier est une approche de test, à mesurer avant montée en charge. L'index des votes et les projections de membres du contrat V2 restent à raccorder.

Tests : npm test. Démarrage local : npm install puis npm start uniquement avec secrets de test et activation explicite. Aucun déploiement serveur à ce stade.

## WebSocket — branche test-chat-websocket uniquement

Première étape de migration du chat : réception des vues autorisées sur `/chat/live`, abonnement authentifié avec ID token Firebase dans le premier message (pas dans l'URL). Origine et identité de test contrôlées, droits de salle et avertissements privés revérifiés via chatView à chaque publication. Une observation RTDB partagée par le processus, active uniquement lorsqu'il existe des abonnés authentifiés. Les messages inchangés ne sont pas rediffusés; les ajouts et l'éviction de l'historique sont envoyés sous forme de delta. Reconnexion temporisée et retour au GET existant tant que le socket ne délivre pas une vue valide. Les envois, rappels, sanctions et signalements restent sur les routes HTTP existantes. Aucun changement visuel intentionnel.

Activation volontaire, uniquement sur environnement de test : ENABLE_TEST_CHAT_WEBSOCKET=true (API) et VITE_TEST_CHAT_WEBSOCKET=true (front). Ces deux variables sont désactivées par défaut. Ne pas changer la branche déployée ni activer ces variables avant npm install, npm test et validation des deux builds; tester ensuite sur Firebase indépendant. Le serveur utilise ws, et la vue complète n'est jamais envoyée sans contrôle de l'identité. Mesurer CPU/mémoire, rafale de reconnexions, droits révoqués, latence, échecs de vérification et 1 000 utilisateurs simulés avec votes en parallèle. Le compteur REST actuel ne mesure pas le trafic de l'observation RTDB: compléter cette instrumentation avant de s'appuyer sur le garde-fou de budget. Le quota de connexions et la limitation de vérification sont des paramètres de test, pas une preuve de capacité.

**Stockage non migré à ce stade.** Les transactions actuelles du chat et les rappels utilisent la même base que le jeu, et certaines opérations effectuent des lectures/écritures REST à la racine. Le WebSocket supprime le polling des clients connectés mais ne supprime pas ces échanges. Pour une migration complète : stockage persistant indépendant (Postgres ou SQLite sur disque persistant payant à instance unique), séparation de la modération et des rapports, identités et adhésions validées côté serveur, réinitialisation et rappels avec opérations idempotentes et réconciliation; test de compatibilité avant bascule. Ne pas utiliser le disque éphémère de Render gratuit pour conserver les messages. Aucun changement Render, Firebase ou facturation effectué.
